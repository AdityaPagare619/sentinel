# REPEATABLE DEPLOY — `sentinel-platform` (Vercel backend)

**Owner:** Team 3 platform/infra · **Tier:** production API (`production-api`) ·
**Date:** 2026-10-07 · **Status:** procedure v1, verified by re-run (see §8)

> This is the click-ops killer. Every production deploy of the Vercel
> backend follows these steps, in order, with the deploy record filled in.
> A deploy that cannot name its commit, its deployment id, and its
> verification evidence did not happen — it was click-ops.

Companion docs: `deploy/vercel/README.md` (what the tier is),
`docs/planning/production/PRODUCTION-STAGES.md` §8 (the rollback plan —
read it before you deploy, not after).

## 1. What a deploy is

One Vercel serverless function serving the exact `PlatformApp` WSGI app
from `platform/server` + the engine package from `src/sentinel`, per
`deploy/vercel/vercel.prod.json` (every `/api/*` → `/api/index.py`).
The bundle is generated by `deploy/vercel/build-bundle-prod.sh` from a
**clean** git tree at a **named commit**. The bundle carries
`BUILD_INFO.json` with that commit — bundle-vs-source drift is checked,
not assumed.

What the tier is NOT: the paging receiver, the gate, the forwarder. This
tier is read-path + safety-state only. The kill-switch endpoints exist
but flip a per-instance flag nothing on this tier reads (honestly marked
`NO-OP LEVER` in the console; externalization RFC:
`docs/planning/rfc/platform-kill-state.md`).

## 2. Preconditions (all must hold before §3)

1. `git ls-remote origin main` matches the commit you intend to ship.
   (A prior wave had silent push failures — trust nothing unverified.)
2. Working tree clean: `git status --porcelain` empty. The build script
   refuses dirty trees (exit 2); `--allow-dirty` is dev-only and records
   `dirty=true` in `BUILD_INFO.json` — never ship an allow-dirty bundle.
3. `scripts/ops/pre-pr-gate.sh` GREEN on the merge commit (no `--fast`).
4. The merge-checklist record exists for the change
   (`docs/planning/production/PROMOTION-GATES.md`).
5. You know the current production deployment id (from the last deploy
   record) — it is your Hobby rollback target (§7).
6. Aditya's hand-test window: if a hand-test is in flight on the current
   deployment, the deploy waits. Deploying under a live hand-test
   invalidates its evidence. (Standing: do NOT redeploy during his
   hand-test; this procedure documents the path, it does not authorize
   the timing.)

## 3. Build the bundle

From the repo root, on the clean tree:

```bash
bash deploy/vercel/build-bundle-prod.sh
```

The script: records `BUILD_INFO.json` (commit, branch, dirty flag, UTC
timestamp), copies `platform/server/*.py` → `api/_srv` and
`src/sentinel/*.py` → `api/_eng/sentinel`, lays
`deploy/vercel/api/index-prod.py` down as `api/index.py`, installs
`vercel.prod.json` as `vercel.json`, and runs the state-exclusion guard
(no keystore/token/audit file may ship). Then it prints the **DEPLOY
RECORD** block — paste it into the deploy note (§5) before proceeding.

Sanity: `python3 -c "import json;print(json.load(open('deploy/dist-prod/vercel/BUILD_INFO.json'))['commit'])"`
must equal the commit from precondition 1.

## 4. Ship it — three paths, one record

Pick ONE. All three produce a deployment id; all three require the same
verification (§6).

### 4a. Vercel CLI (preferred — the command stays in the record)

```bash
cd deploy/dist-prod/vercel
vercel deploy --prod --yes   # project sentinel-platform
```

Keep the immutable deployment URL + id from the output. Verify that
artifact (§6) before treating the deploy as done. Pin the CLI version
you used in the deploy record (automation must not silently change
mid-release — flaviocopes Vercel course).

### 4b. Dashboard redeploy (click-ops, documented not recommended)

Dashboard → project `sentinel-platform` → Deployments → ⋯ on the target
deployment → **Redeploy** (uncheck "use existing build cache" when the
bundle contents changed). Record the new deployment id by hand. This is
the path of last resort: it leaves no command in the record, so the
deploy note (§5) carries the full burden of proof.

### 4c. MCP `upload_file` path (agent-driven deploys)

Method note (redeploy lane, 2026-10-07 — verified in the incident where
the agent briefly shipped a partial 47/66-file deployment and
self-caught):

- `upload_file` **works despite the 403 mask**: the MCP wrapper reports
  403 while the upload actually succeeded. **Never retry on the mask
  alone** — verify by fetching the deployment/URL first; a blind retry
  creates duplicate deployments.
- **argv ceiling ~128KB** (`MAX_ARG_STRLEN`): large file sets cannot go
  inline — they go as **sha-refs**, not file contents. The working dance
  for this repo's ~66-file bundle is: upload the 19 changed files as
  content, reference the remaining 47 by sha from the previous good
  deployment.
- After upload, confirm the deployment id and run §6 against it. The
  partial-deploy incident (47/66 files → production 404s, self-caught
  within minutes, redeployed last-good) is why §6 exists: a deploy is
  not done when the upload returns, it is done when verification passes.

## 5. The deploy note (required)

One note per deploy, kept where the coordinator can find it (deploy
records live in `docs/planning/production/` or the lane doc — never only
in chat). Contents:

- The DEPLOY RECORD block from §3 (commit, bundle sha256, builder,
  exact deploy command, deployment id).
- What changed since the previous production deployment (commit range).
- The verification evidence from §6 (command outputs, not "looks good").
- Env-var changes made alongside (or "none") — see §7: env vars are NOT
  rolled back, so a var change must be recorded deliberately.

## 6. Verify — the deploy is not done until this passes

Run against the **new deployment's URL** (immutable deployment URL
first, then the production alias). All commands unauthenticated except
where noted. Any failure → §7.

```bash
BASE=https://<deployment-id>.vercel.app   # then re-run with the prod alias

# 1. Liveness — 200, unauthenticated, no-store
curl -si "$BASE/api/v1/health/live" | head -8
# expect: HTTP/1.1 200, X-Sentinel-Deployment: production-api, Cache-Control: no-store

# 2. Auth still fail-closed — 401 before any body work
curl -si "$BASE/api/v1/ops/health" | head -3
# expect: HTTP/1.1 401 {"error":"unauthorized"}

# 3. Kill endpoint unauth — 401 fast (regression: must not 500/200)
curl -si -X POST "$BASE/api/v1/safety/kill" | head -3
# expect: HTTP/1.1 401

# 4. CORS preflight regression — LOWERCASE origin (the 2026-10-07 bug was
#    case-sensitivity: mixed-case Origin got no ACAO header)
curl -si -X OPTIONS "$BASE/api/v1/ops/health" \
  -H "Origin: https://adityapagare619.github.io" \
  -H "Access-Control-Request-Method: GET" | grep -i "access-control-allow-origin"
# expect: access-control-allow-origin: https://adityapagare619.github.io  (+ 204)

# 5. Evil origin gets nothing (CORS allowlist, no reflection)
curl -si -X OPTIONS "$BASE/api/v1/ops/health" \
  -H "Origin: https://evil.example" \
  -H "Access-Control-Request-Method: GET" | grep -i "access-control-allow-origin" || echo "no ACAO — correct"

# 6. Bundle provenance — the deployed bundle names its commit
#    (authed; operator token required — Aditya's action if the lane has no token)
curl -s -H "Authorization: Bearer $SENTINEL_OPERATOR_TOKEN" \
  "$BASE/api/v1/ops/health" | python3 -c "import json,sys; print(json.load(sys.stdin))" | head -c 400
# expect: kill_state_scope present (per_instance_tmp until the kill-state RFC lands)
```

The old bundle reproduces the missing-ACAO failure — run check 4 against
the *previous* deployment too when diagnosing: if old fails and new
passes, the fix is discriminated, not assumed.

**Authed checks** (operator token — provisioned in the Vercel dashboard;
Aditya's action): `GET /api/v1/ops/health` → 200 with `environment`,
`safety.kill_switch` (`armed|engaged`, `kill_state_scope`), and
`forwarder.identity`. `GET /api/v1/safety/status` → 200 with `engaged`
and `instance_id`.

## 7. Rollback — read before you need it

Full plan: `docs/planning/production/PRODUCTION-STAGES.md` §8. The
honest summary, verified against
https://vercel.com/docs/instant-rollback (2026-10-07):

- Dashboard → project → Production Deployment tile → **Instant Rollback**.
- **Hobby = previous deployment only.** There is no older target. Older
  than that: revert in Git and redeploy — there is no other path.
- Rollback does **not** rebuild and does **not** touch environment
  variables. A rollback after an env-var change keeps the NEW vars —
  set them deliberately, with eyes open, and record it in the deploy
  note (§5).
- **The trap:** after a rollback Vercel turns OFF auto-assignment of
  production domains. Subsequent pushes build successfully and do NOT go
  live until **Undo Rollback** (dashboard) or `vercel promote
  <deployment-id>`. Builds looking healthy while the site doesn't move
  is the signature of this trap.
- The old `docs/deploy-production.md` systemd/`:8080` rollback ("stop,
  check out, restart") describes a phantom topology — it is the
  customer self-hosted engine doc, not this tier. Do not follow it here.
- The kill switch is **not** a rollback mitigation (no-op lever on this
  tier; receiver path unwired; semantics undecided — P0-1). The fastest
  mitigation is Instant Rollback.

## Pre-mortem — how this procedure fails (written 2026-10-07)

Assumed it is three months from now and a deploy caused an incident.
The causes, and what in this procedure stops each:

1. **Dirty-tree bundle shipped; nobody can name the commit.** → §2.2 +
   the script's exit-2 refusal. Residual: `--allow-dirty` exists — a
   tired operator uses it "just this once." The `dirty=true` in
   `BUILD_INFO.json` and the deploy record make the sin visible; the
   merger's checklist (PROMOTION-GATES.md) rejects allow-dirty bundles.
2. **Two bad deploys in a row; the Hobby rollback target is also bad.**
   → §2.5: know your rollback target before deploying. If the previous
   deployment is suspect, the deploy waits for a known-good — there is
   no older Instant Rollback on Hobby.
3. **Env var changed with the deploy; rollback keeps the new var; old
   code + new var misbehave.** → §5 records var changes; §7 states the
   rule loudly. Residual: Vercel gives no atomic code+var cutover on
   Hobby — accepted, documented, not wished away.
4. **403-mask retry creates duplicate deployments; traffic splits
   across two "production" deploys.** → §4c: verify-before-retry. The
   deployment id in the record disambiguates.
5. **Rollback done; next push builds but doesn't go live; team debugs
   the app for an hour.** → §7 names the auto-assignment trap and the
   `vercel promote` recovery. The signature ("builds healthy, site
   doesn't move") is in the doc so the next operator pattern-matches it.
6. **Deploy lands during Aditya's hand-test; his kill→re-arm evidence is
   invalidated and nobody notices.** → §2.6: the deploy waits. The
   coordinator owns the window.
