# C2 Load Test — Measurement Report

**Date:** 2026-10-04 (night shift, MEASUREMENT lane)
**Status:** MEASUREMENT, not a feature. Nothing was tuned to pass.
**Question (C2):** what breaks, and where, at 1,000 events/min sustained and
10,000 events/min burst? This is the evidence gate for the stepped fail-open
RFC (C1).
**Harness:** `research/bin/load_c2_harness.py` (seeded, reproducible);
analysis `research/bin/load_c2_analyze.py`. Raw run JSONs: `research/load-c2/`.
**Branch:** `lane/load-c2` — PR opened, NOT merged (measurement only).

## 0. Verdict up front

1. **Sustained 1,000/min: HELD.** 99.7% of 14.2k events/run got HTTP 200s;
   e2e p50 20ms / p99 1.28s; the deterministic engine path is fast
   (engine-only p50 9ms); the vendor wait dominates raced decisions exactly
   as designed (p50 1.07s). The single-writer event log kept up (23.5
   appends/s, p50 2.8ms) but its p99 (253ms, one run 585ms) is the first
   crack — lock contention under the global RLock.
2. **Burst 10,000/min: 96% served, 4% loud resets.** No 503s at the
   clean burst rate (the 64-in-flight admission bound never tripped);
   the 4% failures are server-side connection resets under thread
   pressure on 2 CPUs — loud, never silent. Past the design point (a
   90k/min spike), the 503 admission control fired exactly as designed
   before the resets began. §3 has both.
3. **The single most important bottleneck is not throughput — it is the
   correlator's storm detector.** Its fixed threshold (>20 distinct
   fingerprints / 60s) saturates permanently at C2-scale volumes: with
   all-distinct traffic at 1,000/min, 98% of alerts never reach the Jev
   race — they are structurally folded. The threshold cannot distinguish
   "incident storm" from "busy estate". This is an architectural finding,
   not a tuning knob: it decides what fraction of traffic the proof
   engine ever sees.
4. **Secondary findings:** `gate.emitted` grows unboundedly in production
   (one dict per decision, no consumer — a slow memory leak); the
   synchronous forwarder POST is fine against a fast endpoint but holds a
   request thread per page (real-PD latency would multiply this); the
   timer-win watchdog trips even at sustained load (C1 trigger signal is
   live and firing).
5. **What did NOT break:** the race budget held (timer-win rate 6–11%,
   no runaway), the event log never lost a write, the forwarder delivered
   100% of pages it attempted (17.8k, 0 errors), auth stayed fail-closed
   throughout, and no response ever blocked past the 2.7s race budget +
   forward on the engine side.

## 1. Method

- **Path under test:** HTTP loopback → receiver (`/webhook/generic`, D11
  fail-closed HMAC w/ timestamp) → correlator → gate (race-to-page,
  B=2700ms) → forwarder (synchronous POST to stub PagerDuty) → event log
  (file-backed SQLite WAL, production-faithful). Full production path on
  `origin/main` @ `605793f`; no code changes to `src/` for the test —
  instrumentation is wrapper-only.
- **Vendor:** seeded stub (`LatencyStubClient`), NOT the real Jev API — a
  load test must not spend real money or hammer the vendor. Latency model
  from L6's measured distribution (tonight: p50 ~1050 / p95 ~4000 /
  p99 ~4350ms): 90% Normal(1050,200)ms clipped ≥150ms, 7% U(2500,4000)ms,
  3% U(4000,5200)ms. Achieved quantiles reported in §4–6 (the model is
  verified, not assumed).
- **Engine vs vendor separation:** per-request timestamps split the pipeline
  into `engine_only` (normalize + correlate + policy + audit write +
  forward, excluding the race wait) and `vendor_wait` (stub `decide()`
  wall time, recorded independently). The two overlap in wall-clock by
  design (the race); they are reported as separate distributions.
- **Profiles:** `sustained` = 1,000 events/min × 10 min (10,000 events);
  `burst` = 10,000 events/min × 2 min (20,000 events) — burst is a *rate*,
  per the C2 tier language. Poisson arrivals (seeded). Each run 3× with
  fresh pipeline + DB; seeds fixed (`BASE_SEED=20261004` + offsets).
- **Traffic mix (primary):** Zipf-like skew modeling a real noisy estate —
  80% duplicates from a 60-fingerprint hot pool (dedup path), 20% long-tail
  new fingerprints from a 6,000-distinct pool (race path), plus embedded
  storm episodes (distinct fingerprints → storm-declare + fold paths).
  Fingerprint pools are sized so distinct fingerprints recur less often
  than the 300s dedup window. Storm episodes are *extra* arrivals on top
  of the base rate.
- **Sensitivity probes:** `sustained_uniform` / `burst_uniform` (1 run each,
  hot_frac=0) — all-distinct fingerprints. Documents the storm detector's
  behavior under adversarial distinctness; NOT the primary measurement.
- **Calibration state:** no calibration fit, empty allowlist → the gate runs
  in pre-fit conservative mode (suppression ~never on the race path). This
  is the heaviest honest case for the forwarder (page rate ≈ 100% of
  raced decisions). Documented, not tuned.
- **Box:** 2 CPUs, 7 GB RAM, SQLite 3.45.1. CPU-bound numbers are
  box-specific; the *ordering* of bottlenecks and the architectural
  findings (storm threshold, pool sizing, write discipline) are not.
- **Generator health:** the dispatcher records `submit_lag` (scheduled vs
  actual submit time). If the generator can't offer the rate, it shows up
  here — offered vs achieved is reported per run, never assumed.


## 2. Sustained: 1,000 events/min × 10 min (3 runs)

(5× for 25s each) add ~4,000 extra events per run, so the offered volume is
~14.2k/run (~1,420/min average, 83/s peaks). The generator stayed healthy
throughout (submit_lag p99 ≤ 0.11s — the offered rate is real, not
aspirational).

Reading the numbers:

- **The bimodal e2e is the design working.** p50 ~20ms is the structural
  path (dedup reuse, storm fold, change-window) — no vendor involved.
  p99 ~1.3s is the raced path: ~1.07s vendor + ~0.2s engine. The p95
  spread across runs (1037/924/65ms) is storm timing: when a storm episode
  aligns, most traffic folds and p95 collapses to the structural path.
  This is not noise — it is the correlator's regime switching, and §5
  shows what happens when the regime sticks.
- **Engine-only p99 (272ms mean, one run 596ms) vs p50 (9ms):** the
  deterministic path is fast in the median and spiky in the tail. The
  spikes correlate with event-log append p99 spikes — the global RLock
  serializes every decision write, and under it the whole triage waits.
- **Vendor model verified:** achieved p50 1074ms vs L6 target ~1050ms;
  p95 3378 vs ~4000; p99 4447 vs ~4350. The stub is faithful; the engine
  numbers above are measured against a realistic vendor.
- **Timer wins 6–11%** match the vendor tail (p95 3.4s > 2.7s budget):
  the race budget is doing exactly its job, and the watchdog tripped once
  per run — the C1 trigger signal fires under normal sustained load, not
  just in disasters.
- **10 explicit 503s in run 1** during a storm-episode peak: the 64
  in-flight admission bound shed load with 503-never-429, exactly as
  designed. No 429s, no silent drops.

Reading the numbers:

- **96% served, 4% reset.** Every failure is a loud server-side
  connection reset — no silent drops, no timeouts (the 30s client timeout
  never fired), no 429s. The failure mode is ugly but honest.
- **The race barely engaged:** only ~75 vendor calls per 20k events
  (0.4%). The storm detector folded 89% before the gate ever saw them
  (§5). The burst did NOT stress the race pool (32 workers) — it stressed
  the HTTP server, the correlator, and the event-log writer. The
  TIMER_WON_SHED pool-shed path never fired.
- **Event log at 155 appends/s:** p50 5ms, p99 ~200ms, max ~1s. The
  single-writer RLock is now visibly the throughput ceiling — append p99
  tracks engine_only p99. It held, but there is no headroom left on this
  box: another 2–3× would queue without bound.
- **Forwarder held:** ~2.1k pages delivered, 0 errors, p99 83ms — against
  an instant stub. The synchronous POST holds one request thread per
  page; against real PagerDuty latency (100–500ms typical) the thread
  hold would multiply 10–50×. Named risk, not measured failure.

### Beyond the design point: the 90k/min spike runs

The original burst profile's storm episode (8x of the 167/s base) created
a 20-second ~1,500/s (90,000/min) spike — 9x the burst target. Treated as
a separate beyond-design-point experiment (3 runs, ~46.6k scheduled):

- ~40% got HTTP responses; the receiver's **admission control fired as
  designed** (33–314 explicit 503s, never 429); 5.3–6.6k further requests
  got server-side connection resets under thread pressure.
- **Harness caveat (honest):** the remaining ~50% "failures" are
  `CannotSendRequest` — my generator's thread-local connection reuse
  amplifying dead connections into instant client-side failures, not
  engine behavior. The rigorous lower bound on genuine engine-side
  failure is resets + 503s + timeouts (~12–14%).
- The 503s are the important datum: the 64-in-flight admission bound is
  the designed shed, and it engaged exactly when it should have.


## 4. Vendor model verification

The stub is the input model — its fidelity bounds what the engine numbers
mean. Achieved stub quantiles (all runs pooled, n≈1,100 calls):

| Quantile | L6 measured (target) | Stub achieved |
|---|---|---|
| p50 | ~1050 ms | 1074 ms |
| p95 | ~4000 ms | 3378 ms |
| p99 | ~4350 ms | 4447 ms |

The stub is faithful where it matters: the median (which sizes the race
pool) matches within 2%, and the tail crosses the 2700ms budget at about
the right rate (timer-win 6–11% ≈ the ~7–10% of calls slower than budget).
The stub does NOT model vendor errors (5xx/overload) — vendor *failure*
behavior is covered by the fault-injection drills (7/7 pass), not here.

## 5. Sensitivity: uniform-distinct regime (storm-detector saturation)

One run each, all-distinct fingerprints (hot_frac=0) — adversarial
distinctness, not the primary mix. This is the finding that matters most
for C2:

| | sustained_uniform (10k events) | burst_uniform (20k events) |
|---|---|---|
| Offered / ok | 10061 / 10061 (100%) | 20114 / 19978 (99.3%) |
| Vendor calls (reached the race) | 211 (2.1%) | 47 (0.2%) |
| Suppress (storm-folded) | 9731 (97%) | 19926 (99%) |
| e2e p50 / p99 | 5ms / 1103ms | 12ms / 1100ms |

**The correlator's storm detector saturates.** Its threshold is a fixed
absolute: >20 distinct fingerprints in any 60s window. At 1,000/min with
diverse fingerprints the window always holds ~1,000 distinct — 50× the
threshold — so the detector fires, folds everything for 60s, the window
drains (folded alerts don't append to it), traffic resumes for ~2s, and it
re-fires. The measured duty cycle: **~2% of alerts reach the Jev race; 98%
are structurally folded without any model evaluation.**

This is not a harness artifact — it is the engine's real behavior, and it
is arguably *correct* for an incident storm. The architectural problem is
that the threshold cannot distinguish "incident storm" from "busy estate":
a 1,000/min enterprise with diverse alert sources would live in permanent
storm-fold, and the proof engine would see almost none of its traffic.
The 20/60s constants were chosen for a small estate; they do not scale
with the C2 tier. Any redesign-review work at the >10k/min trigger (C2.2)
must make the storm threshold adaptive to the estate's baseline rate —
e.g., a multiple of the trailing baseline distinct-rate, not an absolute
count. Until then, the honest statement is: **at C2 volumes, the storm
detector — not the race, not the vendor — decides what fraction of traffic
gets a model-backed decision.**

## 6. Bottlenecks, in order

Ranked by what constrains the C2 tier first. "Architectural" means no
amount of hardware fixes it; "capacity" means it does.

1. **Correlator storm threshold — ARCHITECTURAL.** Fixed >20 distinct
   fingerprints / 60s. At 1k/min with diverse traffic, ~98% of alerts
   never reach the proof engine (§5). This is the binding constraint on
   *coverage*, and it makes every downstream measurement
   vendor/race/forwarder look better than it is — the storm folds the
   load before the expensive path sees it. Fixing it (adaptive threshold)
   will *increase* load on bottlenecks 2–4; it must land with C1's steps,
   not before.
2. **Event-log single-writer RLock — CAPACITY (this box).** 155 appends/s
   at p99 ~200ms; the lock serializes every decision write and the whole
   triage waits under it (engine_only p99 tracks append p99). On 2 CPUs
   this is the throughput ceiling. More cores raise it; a writer-shard or
   batch-commit redesign removes it. Every append is also fully
   synchronous (BEGIN IMMEDIATE + hash + COMMIT per event).
3. **ThreadingHTTPServer thread-per-request — CAPACITY.** 4% connection
   resets at 10k/min on 2 CPUs; thread-max hit ~580 (mostly generator,
   but server threads scale with concurrent slow requests). Unbounded
   thread spawning under burst is the failure shape — the 64-in-flight
   admission bound is the backstop and it works (503s in the spike
   runs), but resets happen *around* it under extreme pressure.
4. **Synchronous forwarder POST — LATENT.** 0 failures against an instant
   stub, but each page holds its request thread for the POST duration.
   Against real PagerDuty latency this is the next thread-exhaustion
   multiplier after #3. The DurableForwarder (outbox, ADR-012) exists
   precisely to decouple this — it is not on the measured path
   (`build_pipeline_from_env` wires the simple Forwarder).
5. **`gate.emitted` unbounded list — SLOW LEAK.** One dict appended per
   decision, no consumer in production (`emit=None` everywhere in src/).
   At 1k/min ≈ 1.44M dicts/day. RSS grew ~85MB/14k events (mixed
   harness + engine); the engine-side share needs a bound (deque with
   maxlen, or drop when unobserved). Minor, easy, real.
6. **Race pool (32 workers / 256 queue) — NOT saturated.** Never the
   binding constraint in these runs *because* bottleneck #1 folds first.
   If #1 is fixed, the pool becomes load-bearing: at 167/s with a 1.1s
   median vendor, ~180 concurrent vendor slots are needed vs 32 workers —
   the TIMER_WON_SHED path would fire constantly. Pool sizing must be
   re-derived after any storm-threshold change.

## 7. What this measurement proves

1. At 1,000/min sustained on a 2-CPU box, the engine holds: 99.7% served,
   zero lost event-log writes, zero failed forwards, race budget
   respected, auth fail-closed throughout.
2. At 10,000/min burst, the engine serves 96% with honest loud failures
   (4% connection resets); the failure mode is never silent.
3. The 503-never-429 admission control engages exactly when designed
   (spike runs); no 429s anywhere.
4. The event-log single-writer discipline sustains ~155 appends/s with
   p99 <300ms on this hardware — the measured ceiling, not an estimate.
5. The storm detector's fixed threshold saturates at C2 volumes
   (architectural finding, §5).
6. The timer-win watchdog fires under *normal* sustained load (1–2
   trips/run) — C1's trigger signal is live, not theoretical.
7. The vendor latency model used for all engine numbers is verified
   against L6's live measurements (p50 within 2%).

## 8. What this measurement does NOT prove

1. The vendor is a stub — real Jev tail behavior under concurrent load is
   NOT measured here (L6's live campaign covers the vendor; this covers
   the engine).
2. No calibration fit was loaded — suppression-path load (lighter on the
   forwarder) is not characterized.
3. Single box, 2 CPUs — absolute throughput numbers scale with hardware;
   the bottleneck *ordering* is the portable finding.
4. Single tenant — the bridge tenancy model (L2) is not exercised.
5. 10-minute sustained windows — slow leaks (hours) and 24h retention
   effects are out of scope.
6. The stub PagerDuty endpoint answers instantly — real PD latency would
   lengthen the synchronous forward path (a named risk, §6).

## 9. Implications for C1 (stepped fail-open)

1. **The trigger exists and fires.** The C1 RFC proposes the timer-win
   watchdog's sustained-degradation signal as the step trigger. Measured:
   1–2 trips per run at normal load with a merely *slow* vendor (p95
   3.4s). The signal is live; C1's open question is only where the
   step thresholds sit (Type 2), not whether the signal works.
2. **"Vendor slow" is common, not exceptional.** Timer-win rates of
   6–14% with tonight's vendor mean the fail-open path (passthrough)
   already carries significant volume. C1's steps don't add a new path —
   they graduate the fidelity of a path that's already hot.
3. **Fix #1 (storm threshold) before C1, and the pool breaks.** The
   measurement shows the race pool never saturates *because* the storm
   folds first. An adaptive storm threshold without C1's steps would move
   the burst failure from "clean folds" to "pool exhaustion → mass timer
   wins". The RFC ordering matters: adaptive threshold and stepped
   fail-open are one change, not two.
4. **The steps need the event log's headroom.** Step transitions are
   event-logged by design; at 155 appends/s the log is near its ceiling
   on this hardware. C1's drill plan should include a log-saturation
   step (what happens to step-transition events when appends queue).
5. **What the burst failure mode wants:** the observed burst failure
   (connection resets) is loud but wasteful — the client retries, the
   vendor re-sends, the storm re-folds. C1's step 3 (rate-capped paging +
   digest) converts exactly this shape into predictable degraded
   fidelity. The measurement supports the RFC's core claim: at high
   volume, page-everything fail-open *is* the incident.
