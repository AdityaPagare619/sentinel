**Lane:** RESEARCH LANE A — Sonnet inspirations teardown
**Date:** 2026-10-06
**Sources:** `~/workspace/user/files/sentinel-console-v2.html` (25 KB, 111 lines), `~/workspace/user/files/Sentinel_console__simulated.html` (26 KB, 125 lines)
**Method:** full code read of both files (all markup, CSS, and JS logic), cross-checked against the handover prompt's requirements and falsifiers. Every claim below cites the mechanism in the file, not an impression.
**Standing rule for this document:** no aesthetic opinions. Only functional judgments tied to requirements, user flows, or falsifiers. Backend terms are translated to plain English on first use.

## 1. WHAT EACH FILE IS

### File A — `sentinel-console-v2.html`
A light, paper-like console (pale green-gray background, serif headlines) with four surfaces: **Needs you** (the queue), **Suppressed** (the proof ledger), **Guardrails** (kill switch, policy, auth, AI-vs-timer), and **Phone page** (a simulated PagerDuty call card). A sticky striped SIMULATED banner runs across the top; a pipeline-status strip sits under the wordmark (pipeline health, data age, policy, auth, kill switch). Every number is wrapped in a dotted-underline affordance — clicking it prints "why this number" into the footer. A storm is rendered as one big card with a live signal counter and sparkline. Detail opens in a right-hand panel with a timeline (earliest first) and an appeal button ("Undo suppression: page me now"). Keyboard shortcuts (j/k/Enter/a/Esc) and a footer grayscale-test toggle are included. Data: 3 hardcoded open problems + 10,000 synthetic suppressed problems generated by a seeded random function.

### File B — `Sentinel_console__simulated.html`
A light, neutral console (blue-gray background, system font, dark-mode support) with four tabs: **Now**, **Suppressed**, **Safety**, **Notes**. The header carries a SIMULATED chip, pipeline status, policy chip, kill-switch chip, and a **Scenario selector** (Normal / Storm / AI judge down) that re-renders the whole console in that failure mode. "Now" is a two-column layout: a "Needs you" list + "Handled quietly" grouped-by-reason buttons on the left, a detail card on the right (acknowledge/own/escalate, do-first action, cost of inaction, machine call with confidence bar, timeline). "Suppressed" is a windowed table (25 rows per page) with filters (reason, team, confidence slider, expiring-within-15-min) and inline expandable proof blocks. "Safety" holds the kill switch (two-step arm→confirm), policy, auth status, an AI-vs-timer race bar chart, and a session audit log of human actions. A "Notes" tab contains the designer's research notes and falsifier claims. Data: 3 hardcoded open problems (+1 storm problem in storm scenario) + 10,000 synthetic suppressed problems.

## 2. GOODS — worth stealing

### G-1. Trace numbers: every number carries its why, on demand (BOTH FILES)
- **Where:** File A — `.n` class (dotted underline) on every number; click writes "Why this number: …" into the footer. File B — same `.n` affordance; click opens a fixed bottom trace bar.
- **Why it works:** this is the skeptic's layout implemented as a behavior, not a page. The handover's honesty requirements (every number traceable, never fake-real) are satisfied at the point of reading — the operator never leaves context to verify a claim.
- **Steal-worthy:** yes. This is the single best mechanism in either file. Keep the affordance subtle (dotted underline), keep the readout in-context (not a navigation).

### G-2. Suppression grouped by reason; silence aggregated, proof one click away (BOTH FILES)
- **Where:** File A — "Handled quietly" section: three aggregate counts (duplicates / flapping / known noise), each with an "Inspect proofs" button that jumps to the filtered ledger. File B — "Handled quietly" card: four grouped buttons that open the Suppressed tab pre-filtered.
- **Why it works:** this is the scale problem solved as a behavior. 10,000 suppressions are never listed; they are counted by reason, and the ledger is the second step, not the first. Satisfies the handover's core demand: the unit of attention is the problem, the unit of silence is the group.
- **Steal-worthy:** yes. The grouping must be the default; the raw list must never be the first thing a human sees.

### G-3. The storm as a state, not a list (FILE A, storm card)
- **Where:** File A's storm block: one card with a live signal counter, a sparkline of signals-per-minute, a "Group state" line (grouped by change id, ends after 10 min of quiet), a "Notification state" line (one human paged; the rest held with proof), and one mitigation action.
- **Why it works:** during a flood the operator's job is "is it one thing, and what is the one fix" — the card answers exactly that. The sentence "Grouped is not silenced" is the most honest line in either file: it separates correlation (a machine act) from suppression (a decision with proof).
- **Steal-worthy:** yes — the storm-state UI as a distinct mode, with group-state vs notification-state separated.

### G-4. "Considered, not done" — rejected alternatives shown with the decision (BOTH FILES)
- **Where:** File A — timeline entries tagged `(considered, rejected)`, e.g. "Considered Rule 14 duplicate: no match, rejected." File B — proof block line: "Considered, not done: R-02 always page SEV1/2: no match. R-19 confidence floor: near miss."
- **Why it works:** trust is not built by showing the answer; it is built by showing the machine checked the scary alternatives and ruled them out. This is provenance depth — the operator sees what the machine almost did.
- **Steal-worthy:** yes. Every decision surface should carry its nearest rejected alternative.

### G-5. Kill switch: two-step, contract in plain language, measured — never asserted (BOTH FILES)
- **Where:** File A — kill-switch panel: "What actually happens" (does not page everyone instantly; in-flight decisions resolve as pages), measured flip time in ms via `performance.now()`, last-drill record, canary page record, and the list of code that reads the flag. File B — two-step arm→confirm button, drill record (2026-10-02 03:14, passed), per-flip ms timing.
- **Why it works:** the emergency brake is the one control that must be both instant and un-missable, and both files refuse to let it be a bare button: File A explains the contract, File B prevents the fat-finger. Together they are the complete pattern.
- **Steal-worthy:** yes — combine: two-step arm→confirm + plain-language contract + measured timing + drill record.

### G-6. Machine-proposed rule: preview-before-approve gating (FILE A)
- **Where:** File A's "Machine-proposed rule" panel: the Approve button stays disabled until a preview runs on recent data; after approval, the rule still needs a second human signer and the policy stays unsigned until then.
- **Why it works:** it encodes the governance rule as a forcing function in the UI — the machine proposes, the human cannot approve blindly, and one approval is never enough. The handover's policy-governance requirement becomes a behavior instead of a policy document.
- **Steal-worthy:** yes. Any machine-proposed automation must carry preview-before-approve and visible signer state.

### G-7. Degraded honesty: the UI says what it is NOT doing (FILE A)
- **Where:** File A's Needs-you surface: when the kill switch is on, the AI is down, or the policy is unsigned, a banner reads "Suppression is paused because … N problems that would have been silenced now page." The summary line flips from "N handled quietly" to "0 … while suppression is paused."
- **Why it works:** fail-open is a backend property; this makes it a *visible* property. The operator is never left guessing whether the quiet is real quiet or broken quiet. Satisfies the degraded-mode requirement as a first-class behavior.
- **Steal-worthy:** yes. Every degraded state must announce what the machine stopped doing, not just that something is wrong.

### G-8. Least-sure-first default ordering in the suppression ledger (BOTH FILES)
- **Where:** File A — ledger sorted by confidence ascending ("lowest confidence first, since borderline calls deserve a human look"). File B — same (`flt()` sorts by confidence, then expiry).
- **Why it works:** triage by risk, not recency. The suppressions most likely to be wrong get human eyes first — this is the handover's "sort/filter along the pipeline's dimensions" made concrete.
- **Steal-worthy:** yes. Default sort must be risk-first, with the reason stated in the UI.

### G-9. Appeal as a first-class action that preserves history (FILE A)
- **Where:** File A's suppressed detail: "Undo suppression: page me now" with an optional reason field; after appeal the row stays in the ledger marked "Appealed: a page was issued," and the appeal is written into the timeline with who/when/why.
- **Why it works:** reversibility is the handover's core trust requirement ("page me anyway"). Keeping the appealed row in place — marked, not deleted — preserves the audit trail: the machine's decision and the human's override live side by side.
- **Steal-worthy:** yes — File A's version specifically (see B-3 for File B's anti-pattern).

### G-10. Failure modes are demonstrable: the console can show its broken states (FILE B)
- **Where:** File B's Scenario selector (Normal / Storm / AI judge down): switching re-renders banners, the queue, the race chart, and the suppression table's frozen-history notice.
- **Why it works:** degraded mode is a requirement, and this makes it *inspectable* — an evaluator or a new on-call can see what the console looks like when the AI is down, instead of imagining it. The mechanism (state-driven re-render of every surface) is right.
- **Steal-worthy:** yes as a mechanism — but NOT in the operator's header (see B-5). It belongs in an evaluator/demo harness, behind a clearly separated control.

### G-11. Expiry as a first-class dimension of suppression (FILE B)
- **Where:** File B's suppressed table: every row shows "Expires in N min," and a filter checkbox shows only suppressions expiring within 15 minutes.
- **Why it works:** a suppression is a decision with a lifetime, not a verdict. Surfacing expiry — and letting the operator watch what's about to be re-evaluated — treats suppression as the temporary, reviewable act it is.
- **Steal-worthy:** yes. Expiry belongs on every suppression row and as a filter.

### G-12. Session audit log of human actions (FILE B)
- **Where:** File B's Safety tab: "Human actions (this session)" — every ack, ownership move, escalation, appeal, and kill-switch flip lands in a visible list with timestamps.
- **Why it works:** accountability runs both ways. The machine's decisions are audited; the humans' overrides must be too, or "page me anyway" becomes an unaccountable escape hatch.
- **Steal-worthy:** yes.

## 3. BADS — what fails, and why

### B-1. The queue never fills: scale is narrated, not demonstrated (BOTH FILES — the deepest failure)
- **Where:** File A — `need()` sorts 3 hardcoded problems; the 10,000 are synthetic ghosts counted in copy. File B — `list()` sorts 3–4 hardcoded problems; `need()` subtracts 40 when acked but the item stays in the list.
- **Why it fails (scale test):** the handover's core challenge was "the interface must remain usable when 10,000 problems are open." Both files *tell* you about 10,000 problems and *show* you 3. A triage design evaluated with 3 items proves nothing about triage — you cannot judge attention economics, ordering stability, or queue fatigue from a list that fits on one screen. The scale story is copy, not mechanism.
- **Correct principle:** the instrument must be loadable — even synthetically — with hundreds of open problems, so the ordering, grouping, and fatigue behaviors can actually be seen and judged.

### B-2. The ledger is a feed in disguise: 10-per-page (File A) / 25-per-page (File B) pagination over 10,000 rows (BOTH FILES)
- **Where:** File A — `led()`: 10 rows per page with Previous/Next over 10,000 synthetic problems (1,000 pages). File B — `sup()`: 25 rows per page (400 pages), with the note "Windowed: the screen never holds more than 25 rows."
- **Why it fails (scale test):** windowing the DOM is an engineering bound, not a human bound. No human will click through 400 pages; the filters are the only real navigation, and there is no jump-to-risk, no saved views, no "start with the riskiest beyond the default sort." Pagination at this ratio is the scrolling-card-list problem wearing a table costume — the handover explicitly forbade the endless list, and 400 pages of "Next" is an endless list with extra steps.
- **Correct principle:** the ledger needs risk-ranked navigation (jump to least-sure, jump to expiring, jump to appealed), not linear pagination.

### B-3. File B's appeal ERASES the suppression from the ledger (FILE B — audit-integrity failure)
- **Where:** `appeal()` sets `d.app=true`; `act()` filters appealed items out of the suppressed dataset (`D.filter(d=>!d.app)`); a new page-shaped object is pushed into the Now list.
- **Why it fails (honesty test):** the single most important audit property of a suppression system is that history is append-only. Appealing a suppression *deletes it from the record* and manufactures a new incident object, splitting the trail across two objects. An auditor asking "what did the machine decide here, and who overrode it?" finds a gap where the decision was. File A does this correctly (row stays, marked appealed) — File B's version is the anti-pattern to name and avoid.
- **Correct principle:** overrides annotate history; they never rewrite it.

### B-4. File B labels the timeline "frozen at decision time" — then appends to it (FILE B — honesty contradiction)
- **Where:** the detail card header reads "Timeline, earliest first (frozen at decision time)"; but `ack()`, `own()`, and `esc()` all `push` new entries into the same `p.tl` array.
- **Why it fails (honesty test):** "frozen" is a precise claim. A frozen record that grows is not frozen — it is a live log wearing a frozen label. The distinction matters: the decision-time evidence (what the machine knew) and the post-decision actions (what humans did) must be visually separated, or a reviewer cannot tell which facts the machine acted on.
- **Correct principle:** two sections — "what the machine knew" (frozen) and "what happened since" (live). Never one list with a false label.

### B-5. File B puts the simulator knob in the operator's control plane (FILE B — safety-adjacent design error)
- **Where:** the Scenario selector (Normal / Storm / AI judge down) sits in the sticky header, next to the kill switch chip and the policy chip.
- **Why it fails (3 AM test + safety):** a control that fakes a fleet-wide storm, placed where mode controls live, teaches the wrong muscle memory. In a real console this would be catastrophic; in a simulated file it is still wrong because the handover's law is that simulated controls must never share the control plane with real ones. An exhausted operator must never wonder "did I just simulate that, or did that happen?"
- **Correct principle:** scenario/demo controls live in a separate, clearly marked evaluator harness — never in the operator's header.

### B-6. File A's phone page is a hardcoded prop for one incident (FILE A)
- **Where:** `ph()` renders only `H['H-1']` — the checkout incident. The escalation countdown, ack, and actions exist for exactly one problem.
- **Why it fails (user-flow test):** the handover's primary user is the engineer woken at 3 AM on a phone. A phone surface that works for one canned incident is a storyboard, not a surface — it proves the layout of the answer without proving the mechanism (any page → the five facts → act). File B has no phone story at all beyond responsive CSS.
- **Correct principle:** the phone surface must be data-driven (any problem renders its five facts + actions), or it must not exist yet. A prop is worse than an absence because it looks finished.

### B-7. Single-key acknowledge with no confirmation (FILE A — 3 AM hazard)
- **Where:** the `a` key calls `ack()` on the selected open problem immediately — no confirmation, no undo affordance on the key itself.
- **Why it fails (3 AM test):** acknowledgment stops escalation — it is the one action that silences the system's pursuit of a human. Binding it to a single stray keypress, on a surface navigated by j/k while half-asleep, risks silencing a real page by accident. Speed matters at 3 AM, but irreversible-by-default speed is the wrong trade.
- **Correct principle:** ack must be one deliberate gesture (or key + confirm for keyboard), and every ack must be undoable within a window, with the undo visible where the ack happened.

### B-8. Inconsistent product semantics between the two files (BOTH FILES)
- **Where:** the confidence floor is 0.55 in File A's gate text ("confidence above the 0.55 bar"), 0.60 in File B's proof text ("R-19 confidence floor 0.60"), while both files use 0.70 as the display threshold for the "uncertain/low" confidence bar styling. Rule numbering also drifts (File A: R14/R7/R22; File B: R-12/R-27/R-41/R-33).
- **Why it fails (principal discipline):** two inspirations from the same handover, two different machines. If the semantics (what confidence level means "unsure") aren't stable across designs, no design can be judged — the numbers stop meaning anything. This is exactly the kind of drift the handover's "useful details" were meant to prevent.
- **Correct principle:** the next design pass must fix the semantic constants (floors, thresholds, rule ids) before drawing anything, and both files' numbers must be re-checked against them.

### B-9. Fabricated precision wearing a "simulated" disclaimer (BOTH FILES — honesty-test edge case)
- **Where:** File A — "Track record: 12 of this shape; 0 reviewed wrong (simulated review)"; kill-switch "canary page … delivered in 6 s (simulated record)." File B — "Paged because the AI timed out: N problems" where N increments 1–3 per second by random draw; "last drill 2.8 s" in the header chip.
- **Why it fails (honesty test):** the "SIMULATED" label makes these *legally* honest but *functionally* misleading — they imply processes that don't exist (a suppression review board, a canary paging path, a timeout counter). A disclaimer does not cure a fabricated metric; it just documents the fabrication. The handover demanded "every synthetic number traceable" — traceable to *what generated it*, and "a review process we invented for the demo" is not a traceable source.
- **Correct principle:** synthetic numbers must be traceable to a stated generator ("seeded random draw, seed 11"), and the UI must never imply an organizational process (reviews, drills, canaries) that isn't real. If the drill didn't happen, the row says "no drill recorded" — not a plausible time.

### B-10. The "Notes" tab ships the designer's homework inside the product (FILE B — AI-generic tell)
- **Where:** the fourth nav tab, "Notes": operator mental model, jobs, a research log ("one pass, not the 20-note log asked for"), "Falsifiers run twice," "Not built in this pass."
- **Why it fails:** no production console ships its design process as a nav tab. This is the designer talking to Aditya *through the product* — process theater made navigable. It also reveals the file was built to *demonstrate compliance* with the handover ("falsifiers run twice") rather than to *be* the result of it.
- **Correct principle:** research notes live in the repo, not in the nav. The product's only statement about its design is the design itself.

### B-11. Dead controls labeled as features (FILE A)
- **Where:** the "Edit" button on the machine-proposed rule: clicking it only writes "Edit: change expiry or node scope, then preview again (simulated, not wired)" into the footer.
- **Why it fails (honesty test):** a button that announces its own non-function is the UI equivalent of a prop door. In a simulated file, unwired controls must be visibly marked as not-yet-built (disabled with a "not in this pass" note), not dressed as working features that confess in the footer.
- **Correct principle:** every control is either live or visibly pending. Nothing in between.

### B-12. File 1's comment header claims research lineage it cannot show (FILE A — AI-generic tell)
- **Where:** the HTML comment: "Built from the research log (Linear triage, PagerDuty grouping, OneUptime correlation safety)" and "Not browser-tested."
- **Why it fails:** the file was asked to *do* research first; instead it *cites* research in a comment no user will ever see, and ships untested ("Not browser-tested" inside the deliverable). This is the exact pattern the handover's discipline section warned against: the appearance of method without the method.
- **Correct principle:** research is demonstrated in decisions (and documented in the repo), never claimed in comments. And "not tested" is never an acceptable footnote on a deliverable — it's a reason not to deliver yet.

## 4. THE VERDICT

**Why Aditya didn't like these, in plain language:** both files are checklists wearing a UI. Sonnet read the handover as a spec to render — every requirement got its widget, every falsifier got its named feature (a grayscale *button*, a notes tab *about* falsifiers) — but the handover asked for an *instrument for an exhausted human under load*, and neither file puts you in that human's minute-by-minute reality. They are complete at rest and empty in motion: nothing ever arrives, the queue never fills, the storm never actually stresses the layout, the phone never rings for a second incident. The scale problem — the thing Aditya named as the entire point — is narrated in copy ("10,000 synthetic problems") instead of solved in mechanism.

**The single biggest thing Sonnet misunderstood:** the handover's demand was *dynamics*, not *coverage*. "Simulated mode must feel alive" and "thousands to millions of signals" are not labeling requirements — they are the requirement that the console behave like a living system: problems arrive, the queue reorders, the storm builds faster than the operator reads, the UI compensates (aggregates, ranks, interrupts) instead of just displaying. Sonnet built the nouns of the system and skipped the verbs.

**What the next design must do differently:**
1. **Load the queue.** Even synthetically, the instrument must be shown with hundreds of open problems so ordering, grouping, and fatigue are visible and judgable — 3 hardcoded items prove nothing.
2. **Make time pass.** Problems must arrive, age, escalate, and resolve during the demo; the storm must build. A console for realtime events that sits still is a contradiction.
3. **One tool, every context.** The phone surface must be data-driven (any problem → five facts → act), not a prop for one incident; simulator controls must leave the operator's header.
4. **Fix the semantics first.** Confidence floors, rule ids, and what "frozen" means must be constants before the next pixel — the two files already drifted.
5. **Append-only history.** Nothing a human does — especially an appeal — may delete or rewrite what the machine decided. Overrides annotate; they never erase.

## 5. STEAL LIST — behaviors worth carrying forward

1. **Trace numbers** — every number carries its why on demand, in context (dotted affordance → readout). (Both)
2. **Grouped silence** — suppressions aggregated by reason with one-click filtered proof ledger; the raw list is never the first thing seen. (Both)
3. **"Considered, not done"** — every decision shows its nearest rejected alternative. (Both)
4. **Kill switch: two-step arm→confirm + plain-language contract + measured ms + drill record.** (File A's contract + File B's two-step)
5. **Preview-before-approve** — machine-proposed automation cannot be approved until previewed; signer state visible. (File A)
6. **Degraded honesty banner** — the UI announces what it stopped doing and what that means for the human. (File A)
7. **Risk-first default ordering** — least-sure-first in the ledger, reason stated in the UI. (Both)
8. **Appeal that preserves history** — "undo suppression, page me now" with reason capture; the row stays, marked appealed. (File A — File B's erase-on-appeal is the named anti-pattern)
9. **Demonstrable failure modes** — the console can render its storm/AI-down states, as an evaluator harness, never in the operator's header. (File B's mechanism, relocated)
10. **Expiry as a dimension** — every suppression shows its lifetime and can be filtered by imminent expiry. (File B)
