Why the tier rates differ: 40.2 → 55.0 → 187.4/s

This is not one engine getting faster across tiers — the three tiers ran under different conditions, and the 100K number is the anomaly:

  • 10K — 40.2/s (16 workers): the first real tier run; also the run that surfaced the fail-open ladder race (load-test catch #1), fixed the same day.
  • 100K — 55.0/s (32 workers): environment-depressed. The run started while the box had 0 free RAM — the killed first attempt's in-memory audit log had not released (load-test catch #2). A clean 60-chunk re-run of identical chunks and settings did 157/s; the engine's true rate was ~3x the pressured number. The 55/s measures a memory-starved box, not the engine.
  • 1M — 187.4/s (32 workers): clean box, all fixes in. This is the authoritative number — consistent with the clean 100K re-run (157/s), and with 1,092,876 alerts over 24h of virtual traffic its statistics are the tightest.

Takeaway: the 187/s rate is measured on a clean machine; the 55/s number measures a memory-starved box, not the engine. (Verified against LOADTEST-REPORT.md, §Throughput caveat and catch #2.)

What this test did NOT prove

  • Judgment semantics at volume are modeled, timing is measured (2% real Jev sample, n=444)
  • Virtual time, not real time
  • Single machine — no distributed-systems effects
  • Burst probe: vendor throttles by 10x latency at 40 req/s, not by 429s — practical real-Jev rate is far below the bound
  • Audit used WAL+NORMAL for the test; production fsync-per-commit caps throughput on slow filesystems (60ms on btrfs)
  • The 100K tier's 55/s was environment-depressed (box under memory pressure during that run — see “Why the tier rates differ” above). The 187/s figure comes from the 1M tier on a clean box.
